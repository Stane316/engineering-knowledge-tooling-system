# Feuille de revue humaine — C-R01 et C-R04 (volet H)

**Sprint 22 · 31 octobre 2026 · à remplir par le propriétaire**
**Statut :** ⏳ **en attente** — tant qu'elle n'est pas remplie, C-R01 et C-R04
ne sont pas déclarés « réussi » (règle du document 22 : un cas non exécuté
n'est pas un succès).

---

## 1. Pourquoi ce document existe

Les critères **C-R01** (provenance opérateur) et **C-R04** (version après
modification) sont de type **I/H** : test d'intégration **et** revue humaine.
L'intégration est faite et vérifiée. La revue humaine ne peut pas être faite
par l'agent : elle constate qu'un humain juge le résultat crédible, ce qui
n'est pas mesurable automatiquement.

Cette feuille n'est pas une formalité : elle est la **preuve H** exigée. Sans
elle, le critère reste `indéterminé`.

## 2. Prérequis

```powershell
cd <racine du dépôt>
npm ci
npm run build
$env:EKTS_DATA_DIR = ".\data-revue"
node dist/cli/index.js init
```

## 3. C-R01 — provenance opérable

### 3.1 Objectif

Vérifier que les champs de provenance exigés sont **conservés, lisibles et
non inventés** par l'interface réellement livrée.

### 3.2 Procédure

1. Créer un fichier `prov-revue.json` contenant une provenance où la
   **version est explicitement inconnue** (`"sourceVersion": null`) et où le
   **droit de lecture est refusé**.

2. Ajouter une ressource gouvernée :

```powershell
node dist/cli/index.js add --type article --title "Ressource de revue" --content "Texte de revue." --provenance .\prov-revue.json
```

3. Relire la ressource :

```powershell
node dist/cli/index.js list --json
node dist/cli/index.js get <uuid-retourné> --json
```

### 3.3 Ce que vous devez constater

| # | Constat attendu | Observable ? |
| --- | --- | --- |
| R1.1 | tous les champs de provenance sont présents dans la sortie JSON | ☐ |
| R1.2 | `sourceVersion` reste `null` — **aucune** valeur inventée | ☐ |
| R1.3 | la ressource est **exclue** du corpus gouverné (droit de lecture refusé), avec un motif lisible | ☐ |
| R1.4 | la ressource reste **lisible** : l'exclusion ne supprime rien | ☐ |
| R1.5 | aucun accès manuel à SQLite n'a été nécessaire | ☐ |

### 3.4 Critère de réussite

**5/5** constats cochés. Un seul constat non vérifié ⇒ C-R01 volet H
`indéterminé`.

## 4. C-R04 — version après modification

### 4.1 Objectif

Vérifier qu'un humain constate qu'**aucune preuve rétroactive** n'est possible :
on ne peut pas laisser une ancienne empreinte décrire un nouveau texte.

### 4.2 Procédure

1. Ajouter une ressource avec l'empreinte exacte de son contenu (voir
   `docs/CLI.md` § 3.2.1 pour le calcul).
2. Tenter de modifier le contenu **sans** fournir de nouvelle empreinte.
3. Tenter de fournir l'**ancienne** empreinte sur le nouveau texte.
4. Fournir la **nouvelle** empreinte exacte.
5. Créer une ressource dont la provenance porte une empreinte **sans contenu
   conservé**, puis la lire.

### 4.3 Ce que vous devez constater

| # | Constat attendu | Observable ? |
| --- | --- | --- |
| R4.1 | l'état (1) — version autorisée conservée — est distingué et relu à l'identique | ☐ |
| R4.2 | modifier le contenu sans nouvelle empreinte est **refusé**, avec un motif compréhensible | ☐ |
| R4.3 | réutiliser l'ancienne empreinte sur le nouveau texte est **refusé** | ☐ |
| R4.4 | fournir la nouvelle empreinte exacte est **accepté**, sur le **même UUID** | ☐ |
| R4.5 | une empreinte sans copie conservée est annoncée **« non reconstructible »** | ☐ |
| R4.6 | vous estimez le comportement **compréhensible sans lire le code** | ☐ |

### 4.4 Critère de réussite

**6/6** constats cochés. R4.6 est un jugement humain : c'est précisément ce
que la preuve H apporte et qu'aucun test automatisé ne remplace.
